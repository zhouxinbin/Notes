# Codex 类应用通过 CC Switch 切换供应商时的会话隔离与迁移指南

> 适用场景：Codex、Codex CLI、IDE 扩展或类似应用原先通过 CC Switch、自建代理或其他模型供应商运行，之后切换为 ChatGPT/Codex 官方账号登录，发现旧会话没有出现在任务列表中。

## 一、问题的本质

这类问题通常不是“聊天内容被删除”，也不一定是真正的“账号所有权冲突”，而是以下三层状态没有同步：

1. **认证身份**
   - ChatGPT/Codex 账号登录；
   - OpenAI API Key；
   - 第三方供应商 API Key；
   - CC Switch 或代理服务保存的认证配置。
2. **模型提供方**
   - 官方 OpenAI 提供方通常记为 `openai`；
   - CC Switch 路由可能记为 `cc-switch-official`；
   - 通用代理或自定义端点可能记为 `custom`，也可能使用其他名称。
3. **本地会话索引**
   - 会话正文通常保存在 `$CODEX_HOME/sessions`，默认位置是 `~/.codex/sessions`；
   - Codex 还会使用 SQLite 数据库记录标题、目录、更新时间、模型提供方和会话文件路径；
   - 桌面端任务列表可能只展示当前环境能够识别或加载的提供方记录。

因此，即使两种路由最终都调用 OpenAI 模型，只要 `model_provider`、认证方式、`CODEX_HOME` 或本地索引不同，应用仍可能把它们视为两组会话。

## 二、为什么切换账号后旧会话看不到

### 1. 提供方标记不同

通过 CC Switch 创建的会话可能带有类似下面的元数据：

```json
{
  "model_provider": "cc-switch-official"
}
```

通过官方 ChatGPT/Codex 账号登录后，新会话则可能记录为：

```json
{
  "model_provider": "openai"
}
```

如果桌面端在当前登录模式下只索引 `openai` 会话，旧记录虽然仍在磁盘上，却不会出现在任务列表中。

### 2. 自定义提供方配置已不存在

旧会话记录为 `custom` 时，恢复会话可能需要原来的自定义提供方配置。切换配置或卸载 CC Switch 后，Codex 可能无法解析该提供方，于是隐藏会话或将其标记为不可加载。

### 3. 使用了不同的 `CODEX_HOME`

不同启动器、终端配置或路由工具可能指定不同的 `CODEX_HOME`。此时两边读取的是完全不同的会话目录和数据库，修改提供方标记也无法解决问题。

### 4. 本地会话与云端会话不是同一种数据

本地 Codex 会话、ChatGPT 网页聊天和 Codex 云任务不应混为一谈。本地迁移只能处理本机保存的会话文件与索引，不能把某个 ChatGPT 账号的云端聊天转移给另一个账号。

## 三、先确认是哪一种问题

### 1. 确认当前认证方式

```bash
codex login status
```

也可以在 Codex 或 ChatGPT 桌面端的个人资料菜单中确认当前账号和工作区。

### 2. 确认会话目录

默认目录为：

```text
~/.codex/sessions
```

如果设置了 `CODEX_HOME`，应以该目录为准。不要假设 CC Switch 和官方登录使用了同一个目录。

### 3. 查找状态数据库

不同版本的文件名可能不同，常见形式为：

```text
~/.codex/state_5.sqlite
~/.codex/state_*.sqlite
```

先只读检查：

```bash
find ~/.codex -maxdepth 1 -name 'state_*.sqlite' -print
sqlite3 ~/.codex/state_5.sqlite '.tables'
sqlite3 ~/.codex/state_5.sqlite '.schema threads'
```

只有在数据库确实包含 `threads` 表，并且字段中存在 `model_provider` 和 `rollout_path` 时，后续示例才适用。

### 4. 统计不同提供方的会话

```bash
sqlite3 -header -column ~/.codex/state_5.sqlite \
  "SELECT model_provider, thread_source, COUNT(*) AS count
   FROM threads
   GROUP BY model_provider, thread_source
   ORDER BY count DESC;"
```

常见的 `thread_source`：

- `user`：用户可见的主会话；
- `subagent`：主会话产生的内部子代理会话，通常不会单独显示在侧边栏。

### 5. 检查会话文件中的提供方标记

```bash
rg -n -o '"model_provider"\s*:\s*"[^"]+"' ~/.codex/sessions -g '*.jsonl'
```

不要直接全局替换。先确认哪些提供方名称确实来自需要迁移的 CC Switch 路由，避免误改其他仍在使用的第三方供应商。

## 四、如何迁移到当前官方 Codex 账号

### 重要说明

下面的操作是**本地会话元数据迁移**，不是 OpenAI 提供的云端账号所有权转让接口。它的目标是：

- 保留原会话 ID、标题、时间和消息记录；
- 把已确认属于旧路由的 `model_provider` 改为 `openai`；
- 让当前官方登录环境重新索引并继续这些本地会话。

执行前应先登录目标 ChatGPT/Codex 账号，并完全退出 Codex 桌面端、CLI 和 IDE 扩展，避免 SQLite WAL 或运行中的进程覆盖修改。

### 第 1 步：设置明确路径

下面以 `state_5.sqlite` 为例。若实际版本不同，请使用刚才确认的完整路径。

```bash
MIGRATION_CODEX_DIR="$HOME/.codex"
MIGRATION_DB_PATH="$MIGRATION_CODEX_DIR/state_5.sqlite"
MIGRATION_BACKUP_DIR="$PWD/codex-session-migration-backup"
mkdir -p "$MIGRATION_BACKUP_DIR"
```

### 第 2 步：备份数据库

使用 SQLite 自带的备份功能，避免直接复制一个可能处于 WAL 状态的数据库：

```bash
sqlite3 "$MIGRATION_DB_PATH" \
  ".backup '$MIGRATION_BACKUP_DIR/state.sqlite.before'"
```

### 第 3 步：生成待迁移文件列表

以下示例假设已确认 `cc-switch-official` 和 `custom` 都属于旧路由。若 `custom` 还被其他供应商使用，应缩小条件，不能全部迁移。

```bash
sqlite3 "$MIGRATION_DB_PATH" \
  "SELECT rollout_path
   FROM threads
   WHERE model_provider IN ('cc-switch-official', 'custom')
   ORDER BY id;" \
  > "$MIGRATION_BACKUP_DIR/session-paths.txt"
```

逐个确认文件存在：

```bash
while IFS= read -r session_path; do
  test -f "$session_path" || {
    printf '缺少会话文件：%s\n' "$session_path"
    exit 1
  }
done < "$MIGRATION_BACKUP_DIR/session-paths.txt"
```

### 第 4 步：备份会话 JSONL

先生成相对于 Codex 数据目录的路径，再归档：

```bash
sed "s#^$MIGRATION_CODEX_DIR/##" \
  "$MIGRATION_BACKUP_DIR/session-paths.txt" \
  > "$MIGRATION_BACKUP_DIR/session-relative-paths.txt"

tar -C "$MIGRATION_CODEX_DIR" \
  -czf "$MIGRATION_BACKUP_DIR/sessions.before.tar.gz" \
  -T "$MIGRATION_BACKUP_DIR/session-relative-paths.txt"
```

建议同时保存校验值：

```bash
while IFS= read -r session_path; do
  shasum -a 256 "$session_path"
done < "$MIGRATION_BACKUP_DIR/session-paths.txt" \
  > "$MIGRATION_BACKUP_DIR/sessions.before.sha256"
```

### 第 5 步：修改会话文件

只修改已列入清单的文件，并且只替换 `model_provider` 字段：

```bash
while IFS= read -r session_path; do
  perl -pi -e \
    's/("model_provider"\s*:\s*)"(?:cc-switch-official|custom)"/$1"openai"/g' \
    "$session_path"
done < "$MIGRATION_BACKUP_DIR/session-paths.txt"
```

会话文件中可能不止一处 `model_provider`：除了 `session_meta`，部分版本还会在后续上下文事件中重复记录，因此需要检查清单内文件的所有精确字段。

### 第 6 步：修改 SQLite 索引

```bash
sqlite3 "$MIGRATION_DB_PATH" <<'SQL'
BEGIN IMMEDIATE;

UPDATE threads
SET model_provider = 'openai'
WHERE model_provider IN ('cc-switch-official', 'custom');

SELECT changes();
COMMIT;
SQL
```

如果只打算迁移部分会话，必须增加 `id IN (...)`、时间、工作目录或其他精确条件，不能使用上述全量条件。

### 第 7 步：验证数据

检查数据库完整性和剩余记录：

```bash
sqlite3 "$MIGRATION_DB_PATH" 'PRAGMA integrity_check;'

sqlite3 -header -column "$MIGRATION_DB_PATH" \
  "SELECT model_provider, thread_source, COUNT(*) AS count
   FROM threads
   GROUP BY model_provider, thread_source;"
```

检查旧标记是否仍存在：

```bash
while IFS= read -r session_path; do
  rg -n '"model_provider"\s*:\s*"(cc-switch-official|custom)"' \
    "$session_path"
done < "$MIGRATION_BACKUP_DIR/session-paths.txt"
```

逐行验证 JSONL：

```bash
while IFS= read -r session_path; do
  jq -e -c . "$session_path" >/dev/null || exit 1
done < "$MIGRATION_BACKUP_DIR/session-paths.txt"
```

全部通过后重新启动 Codex。旧主会话应重新出现在任务列表中；内部 `subagent` 记录通常仍只作为主会话的一部分存在。

## 五、回滚方法

如果迁移后会话无法打开，应先完全退出 Codex，再恢复备份。

恢复数据库：

```bash
sqlite3 "$MIGRATION_DB_PATH" \
  ".restore '$MIGRATION_BACKUP_DIR/state.sqlite.before'"
```

恢复已归档的会话文件：

```bash
tar -C "$MIGRATION_CODEX_DIR" \
  -xzf "$MIGRATION_BACKUP_DIR/sessions.before.tar.gz"
```

重新执行 `PRAGMA integrity_check` 和 JSONL 校验后，再启动 Codex。

## 六、迁移后的影响

### 能够保留的内容

- 本地会话 ID；
- 标题和更新时间；
- 用户消息与模型回复；
- 工具调用记录；
- 主会话与内部子代理历史；
- 原工作目录信息。

### 不会自动迁移的内容

- 旧供应商的余额、套餐和计费记录；
- 第三方供应商后台的日志；
- 另一个 ChatGPT 账号中的云端聊天；
- 旧账号独有的工作区权限；
- 连接器、插件或 MCP 服务的 OAuth 授权；
- 原工作目录中已经移动或删除的文件。

迁移后的旧会话再次运行时，会使用**当前登录账号、当前模型配置、当前权限策略和当前插件状态**，并不保证完全复现旧供应商下的行为。

## 七、安全注意事项

1. **不要编辑 `auth.json` 来迁移会话。**  
   `~/.codex/auth.json` 可能包含访问令牌和刷新令牌，应像密码一样保护，不能提交到 Git、粘贴到工单或分享给他人。

2. **不要把“改账号 ID”当成通用方案。**  
   本地会话表未必存在账号所有者字段。盲目替换令牌中的账号 ID 不但无效，还可能破坏登录状态。

3. **不要在应用运行时直接覆盖数据库。**  
   SQLite 的 `-wal`、`-shm` 文件和应用缓存可能导致修改丢失或数据库状态不一致。

4. **不要无条件迁移所有 `custom` 会话。**  
   `custom` 可能对应多个真实供应商，必须先按会话、时间、目录或模型配置确认来源。

5. **必须同时处理数据库与 JSONL。**  
   只修改数据库可能让列表恢复显示，但继续会话时仍读取旧提供方；只修改 JSONL 则可能仍被索引过滤。

6. **保留可验证的完整备份。**  
   至少备份状态数据库、待迁移 JSONL 文件清单、会话归档和 SHA-256 校验值。

## 八、本次实际案例

在一次从 CC Switch 官方账号路由切换到 ChatGPT Plus/Codex 官方登录的案例中：

- 本地数据库中仍保留全部历史记录；
- 旧会话的提供方为 `custom` 或 `cc-switch-official`；
- 新会话的提供方为 `openai`；
- 当前任务列表最初只展示新的 `openai` 会话；
- 共迁移 17 条本地记录，其中 11 条为用户主会话、6 条为内部子代理会话；
- 数据库和会话 JSONL 同步改为 `openai` 后，11 条旧主会话立即重新出现在任务列表；
- 随机读取旧会话成功，SQLite 完整性和逐行 JSON 校验均通过。

这个案例说明：表面上的“账号之间不共享会话”，实际可能只是本地提供方标记和索引规则不一致。先确认数据仍在，再做最小范围的元数据迁移，比复制令牌或重建会话更安全。

## 九、官方资料与方案边界

OpenAI 官方资料确认：

- Codex 本地工作支持使用 ChatGPT 账号或 API Key 登录；
- ChatGPT 登录使用订阅和工作区权限，API Key 使用 OpenAI Platform 组织的计费与数据策略；
- 登录信息可能缓存在 `~/.codex/auth.json` 或操作系统凭据存储中；
- 本地会话记录默认位于 `$CODEX_HOME/sessions`；
- 自定义模型提供方可以选择 OpenAI 认证、供应商环境变量认证或不认证。

参考资料：

- [OpenAI Codex：Authentication and sessions](https://learn.chatgpt.com/docs/auth)
- [OpenAI Codex：Custom model providers](https://learn.chatgpt.com/docs/config-file/config-advanced#custom-model-providers)
- [OpenAI Codex：Troubleshooting](https://learn.chatgpt.com/docs/troubleshooting)

官方公开资料目前没有提供通用的“本地历史会话账号所有权迁移”命令。本文中的数据库与 JSONL 修改方案来自对本地存储结构的实际检查和迁移验证，应视为有备份保护的本地修复方法，而不是官方云端迁移接口。不同 Codex 版本可能调整数据库文件名、表结构或索引行为，执行前必须重新检查实际结构。
